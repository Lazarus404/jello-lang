# VM tests

The VM's tests: hand-written `.jlo.txt` fixtures run by the scripts in `tests/ci`, and C tests in
`tests/csrc` for what a fixture cannot reach. `test_vm.sh` builds the VM in a temporary directory
(or `JELLO_VM_BUILD_DIR`), builds them against it and runs them all; it needs the VM alone, no
compiler. The VM is checked here, below Jello: the compiler's tests are `jelloc/tests`, run
by `test_jello.sh` or `jelloc test`.

If you create any new tests, add them to the list below for sanity purposes.

```bash
./scripts/build_vm.sh && ./scripts/test_vm.sh
./scripts/test_x64.sh   # the same, and test_jello.sh, on the x86_64
```

Fixture scripts (`tests/ci`), in the order `test_vm.sh` runs them:

- `bytecode_fixtures.sh` -- `.jlo` round trips, compressed-versus-canonical conformance, and the
  structural and semantic reject fixtures (`tests/bytecode/`, `tests/bytecode/corrupt/`).
- `interp_fixtures.sh` -- every typed numeric opcode, and the six benchmark programs
  (`tests/bytecode/interp/`, `tests/bytecode/bench/`).
- `gc_fixtures.sh` -- `Bytes` opcodes, `NULL_DEREF`/`BOUNDS` traps, roots surviving a forced
  collection, and allocation churn reclaimed under `--gc-stats` (`tests/bytecode/gc/`).
- `dyn_fixtures.sh` -- the Dynamic boundary, boxing, `KINDOF`/`PHYSEQ`, objects, and the
  `TYPE_MISMATCH` traps of `FROM_DYN_*` (`tests/bytecode/dyn/`).
- `jdll_fixtures.sh` -- native calls through a test `.jdll` and signature mismatches rejected at
  load (`tests/bytecode/jdll/`, `tests/jdll/test_native.c`), and the std JDLL (`tests/bytecode/std/`).
- `process_fixtures.sh` -- the process host contract: arguments and exit status.
- `deps_fixtures.sh` -- `jlo_tool init` and `get-deps` against a `file://` registry.
- `packet_fixtures.sh` -- byte-order reads and writes, `BITS_*`, `BYTES_BLIT`, and one packet built
  two ways to identical bytes (`tests/bytecode/packet/`).
- `jir_fixtures.sh` -- `jlo_tool dumpir` against golden JIT IR (`tests/jit/ir/`).
- `fuel_fixtures.sh` -- the `--fuel` and `--max-bytes-len` limits (`tests/bytecode/fuel/`).
- `name_atom_roundtrip.sh` -- name atoms are additive.
- `stress_fixtures.sh` -- frame and `nregs` ceilings, JIT register pressure against the
  interpreter, GC size-class churn, `Bits` and `Bytes` boundaries, and fuel versus stack overflow,
  interpreted and on the JIT (`tests/bytecode/stress/`, generated by `gen_stress_fixtures.py`).
- `jit_numeric_conform.sh` -- each interpreter fixture but `stack_overflow`, run on the JIT through
  `tests/csrc/jit_numeric_run.c` and compared with the interpreter; one that does not compile is
  skipped.

C tests (`tests/csrc`):

- `trap_pc_tests.c` -- trap locations in interpreted and JIT frames.
- `vm_safety_tests.c` -- the VM's safety checks.
- `enum_tests.c` -- enums.
- `thread_tests.c` -- threads sharing one heap: a blocking native call does not deadlock
  the collector, a non-allocating loop still reaches a safepoint, and the std JDLL's file I/O,
  `get_env` and arguments, with one module freed and a different one loaded 20 times, to catch
  frame-cache aliasing when the allocator reuses an address.
- `jir_tests.c` -- `jello_jit_ir_verify` on hand-built IR.
- `jit_frame_abi_tests.c` -- the JIT prologue and epilogue bytes, and a call through them.
- `jit_numeric_tests.c` -- straight-line numeric JIT code, its traps, and register reloads.
- `jit_cfg_tests.c`, `jit_calls_tests.c`, `jit_mixed_tests.c`, `jit_reload_tests.c` -- the JIT's
  control flow, calls, mixed JIT and interpreted frames, and reload.
- `jit_arm64_tests.c` -- arm64 register roles, pools and `BL` patching (arm64 only).
- `jit_golden_tests.c` -- golden JIT bytes for numeric code, branches, calls and Dynamic
  helpers (arm64 only).
- `thread_stress_tests.c` -- stop-the-world allocation from 8 threads, blocking native calls, JDLL
  cycling and JIT reload under contention.
- `capstone_stress_test.c` -- all of that at once, for a sustained run.

Code that executes JIT output runs on arm64 and x86_64 hosts; `test_x64.sh` covers x86_64. The C
tests build with warnings as errors, and the thread and stress tests each start a watchdog
(`watchdog.h`), so a hang fails rather than stalls. Every C test also runs on Windows, so
`poll_tests.c` waits on loopback sockets, all the Windows poller watches.
